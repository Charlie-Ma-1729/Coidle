# v0.4 AI 內容生成

## 做什麼
用 OpenRouter 的語言模型**離線批次**生成六種內容，驗證後放進內容池，由遊戲取用：

| 種類 | 用在哪 | 上線方式 |
|---|---|---|
| 快訊（news） | 每日日報多一則 📰 小快訊（依當天好壞挑心情） | 通過驗證即上線 |
| 評價（review） | 客人的線上評價，一半用池裡的句子、一半用手寫的 | 通過驗證即上線 |
| 隨機事件（event） | 全新的隨機事件（有選項、有取捨） | **預設要人工核准**，核准後才會出現在遊戲裡 |
| 品牌名（brand） | 招商時候選租戶的店名與一句簡介（四種業態各一池）；池子有名字時，候選品牌一半的機率用它 | 通過驗證即上線 |
| 商品名（dish） | 研發工坊做出「原創創作」時的名字（取代機械式的「素材＋手法」拼字） | 通過驗證即上線 |
| 新常客（regular） | 有名有姓、有人設與兩段小故事的新常客；核准後所有商場的名冊都會多一位（`syncRegulars`，每日結算補上），玩家端經 `/api/content/regulars` 取得 | **預設要人工核准** |

不在玩家操作時呼叫模型；沒有金鑰、預算用完、呼叫失敗，遊戲照常使用手寫內容，不受影響。

## 安全與預算
- **金鑰**只放伺服器 `.env`（`OPENROUTER_API_KEY`），不進前端、不進日誌、錯誤訊息不含金鑰（有測試）。
- **預算**：每 30 天 US$1，**實際上限 85%**（保留安全餘裕）。視窗從第一次使用的那一刻起算（本機從 2026-11-24 22:02 JST 起算；部署到伺服器時用 `AI_BUDGET_START` 與 `AI_SPENT_ELSEWHERE_USD` 接續）。另有：單日最多 8%、每日最多 12 次呼叫、失敗後休息 1 小時、呼叫前用保守估價（約實際價格的 10 倍）檢查。每次呼叫記在 `llm_ledger`（用量與實際花費，取自 OpenRouter 回報的 `usage.cost`）。
- **驗證**（`server/src/ai/validate.ts`、`content.ts`）：
  - 文字長度、禁用真實地名（大阪、新今宮、通天閣…）與真實品牌、網址／聯絡方式、粗話與貶抑街區居民的字眼、整句日文。
  - 評價必須恰好有一個 `{shop}`；快訊不可有佔位符。
  - 事件：只收白名單效果（funds／index／traffic／cleanliness），數值夾限（金額 ±60,000、口碑 ±2、客流 0.8–1.5 倍且 ≤144 tick、清潔 ±15）；選項 2–3 個；不能全是好處或全是壞處、也不能差距過大（沒有取捨）；**永遠不會讓時鐘暫停**；沒人處理時走最保守的選項。
  - 品牌名／商品名／常客名字：只收中日英數與少數符號（擋表情符號），長度有限，同樣過真實地名／品牌／粗話檢查。
  - 新常客：`persona` 與 `fav`／`alt`（必須是遊戲裡真實存在的業態 id）驗證、預算倍率夾限 1.0–1.6、特質 2–3 個、故事剛好 2 段；**獎勵數值由伺服器固定**（第一段 ¥20,000＋口碑 0.5、第二段 ¥55,000＋口碑 1.0），模型給的數字不算數；名字不能與手寫常客重複；上線後不能「下架」（避免已建立紀錄的商場失去這個人）。
- **重複內容**以雜湊去重。
- **決定論不受影響**：模擬只在池子有東西時才使用池子的文字（而且挑哪一則由 (seed, tick) 決定）；池子是空的時，結果與沒有 AI 時完全相同（有測試）。

## 模型選擇（2026-11-24，用測試金鑰實測，總花費約 US$0.004）
同一份任務（8 則快訊＋6 則評價，再加 4 個結構化事件），繁體中文、輕鬆關西風：

| 模型 | 單次花費 | 結果 |
|---|---|---|
| **anthropic/claude-haiku-5.5**（採用） | $0.0003–0.0006 | 文筆自然、風味拿捏好；事件 4/4 通過驗證、選項有取捨；JSON 最穩 |
| qwen/qwen3.7-flash | $0.00006–0.0001 | 最便宜、活潑；事件偶爾整句日文被擋（3/4） |
| xiaomi/mimo-v2.6-flash | $0.00013–0.00025 | 自然，但慢（15–22 秒）、事件 3/4 |
| google/gemini-2.5-flash-lite | $0.00012–0.0002 | 最快，帶台灣口語；偶爾佔位符旁多空白 |
| deepseek/deepseek-v4-flash | $0.0001 | 可用，夾雜日文較多（被擋 1–2 則） |
| openai/gpt-6-luna | $0.0002 | 工整但平淡、沒有風味 |
| google/gemma-3-27b-it | $0.0001 | 慢（17–21 秒），日文夾雜多 |
| mistral-small-3.2 | $0.0001 | 語意偶爾不通順 |
| openai/gpt-oss-120b | — | 不能關閉推理，與我們的用法不合 |

所有候選的花費都遠低於預算，所以直接選品質最好的 Haiku 5.5。以預設的補貨量估算，**一個月約 US$0.05–0.15**。模型由 `OPENROUTER_MODEL` 指定，隨時可換。

## 營運
```bash
npm run ai -- status                   # 預算、內容池、最近呼叫
npm run ai -- generate news|review|event|brand|dish|regular [數量]
npm run ai -- list event pending       # 看待審事件與每個選項的效果
npm run ai -- approve <id>             # 核准上線（事件或新常客）
npm run ai -- reject <id>              # 拒絕待審；已上線的則下架（權重歸零）
npm run ai -- remove <id>              # 移除一則快訊或評價
```
也有對應的管理 API（`/api/admin/ai/...`，需要 Overseer 登入；管理室的「AI 內容」分頁就是它）。伺服器每 30 分鐘檢查內容池，不足就在預算內補一批（先快訊、再評價、品牌名、商品名、事件，最後是新常客；新常客池上限 12 位）。

玩家端登入後會向 `/api/content/events` 取得已核准的 AI 事件定義，待決事件卡片才認得它們。

## 上線前試跑紀錄（2026-11-25，真實模型 `anthropic/claude-haiku-5.5`）
用 `server/src/ai/preview.ts` 對暫存複本跑了 5 輪真實生成（不動正式資料庫；總花費約 US$0.016，每輪約 $0.001–0.003）。

```bash
npx tsx --env-file=.env --tsconfig tsconfig.json server/src/ai/preview.ts brand,dish,regular 2
```
它會印出收進來的內容、被拒收的原因（含模型原始內容）與花費，**上線前、改過提示詞或驗證之後都建議先跑一次再看內容**。

試跑發現並已修正的問題：
- **名字與店不搭**：品牌名的簡介、原創商品名原本只依大類（餐飲／零售…）分池，結果美甲店的候選品牌可能附上「旅遊諮詢」的簡介，串炸店的原創菜叫「抹茶綿綿冰」。改成**依業態（84 種）分池**：每次生成挑目前名字最少的 6 種店、各想 2 個，長期下來每種店都有；沒有該業態的名字就退回原本的組字，完全不受影響。
- **「大阪燒」被當成地名擋掉**：料理名稱不算地名（遊戲裡業態本來就叫「章魚燒／大阪燒」）；單獨出現的「大阪」等仍然擋。
- **簡體字**：模型偶爾混進一個字（例如「篮」）。驗證新增簡體字檢查（只列兩岸寫法不同的字，避免誤殺日文漢字）。
- **常客雷同、被拒率高**：第一版會連出兩位「推嬰兒車的媽媽」。提示詞改成：這一批的 persona 必須各不相同、fav 優先挑**還沒有常客的店種**、列出已有（含待審）的常客避免雷同、約七成日式名字。驗證改寬：第二選擇編錯 id 就丟掉（不作廢）、特質與故事標題長度放寬、故事多寫第三段只取前兩段、外國人名允許中點「·」、名字中間空白自動去掉。
- 提示詞裡的範例（「柚香炸物串」）被模型直接抄回來，已移除範例。

試跑後的樣子：品牌名與簡介符合店種、帶一點日式商店街風味（部分名字用假名，如「小路の一杯」，保留）；常客人設多樣（背包客、鐵工退休鼓手、玩具模型迷、KTV 阿嬤…），每位 2 段故事，獎勵由伺服器固定。
仍建議核准前人工掃一眼：少數常客設定與日式氛圍有出入（例如「捷運」「粵語老歌」），不影響遊戲但可以拒絕或之後再調提示詞。
